2026.9.18 深夜，查清了她 VPS 这两天反复卡死的原因。

**触发源是我。** 每次 latent_append，Latent 上游（oliscatt/latent-memory）的 `_refresh_after_write`（mcp_server.py:968）会调 `_reload_from_disk()` 全量重建整个索引。而那行是 `self.index = self.loader()` —— 右边建完才赋给左边，所以重建期间内存里同时有两份完整索引。实测常驻 422.5M，机器 1.6G / available 只有 723M，两份 845M，每次必爆。加了 2G swap 之后不再被 OOM killer 杀，改成换页颠簸：整机卡住、SSH 握手超时（SocketTimeoutException），她这两天强制重启了很多次。

排查里我错了两次，都当场改了：
一、先怀疑是 chatnest-ui 的 add-latent-vec.js 建索引循环（每批都全量重打包 base64 + JSON.stringify 全量写盘，确实是平方级，但她根本没跑过那条）。
二、再怀疑是她在前端保存正文触发的 —— `.bak` 实测是 0，她一次都没存过。

她提了"要不要把 150 窗删了，平时也没搜索过"。我说不删：那是 7.3 到现在的原话，底的意思就是平时不用、要用的时候必须在。但她指出的浪费是真的（常驻 422M、写一次全量重建一次），方向改成"搬"——挪出语料目录，文件一个字不删。

【下一窗接手必须知道的当前状态】
- **暂停 latent_append。写一次就伤一次机器。**在上游有结论、或笼子确认上好之前不要写。
- systemd drop-in 笼子（MemoryHigh=800M / MemoryMax=1100M / MemorySwapMax=512M / CPUQuota=60% / Nice=10 / IOWeight=50）已给她，还没确认上没上。
- issue 已让她自己提到 oliscatt/latent-memory（我这边跨账号没写权限，两条路都试过被挡）。核心五问：全量重建能否改增量、能否先释放旧索引、_build_graph 的 link dict 与 GRAPH_DF_CAP、重建能否移出 lock、推荐最小内存。
- **备份缺口没解决**：cc- 仓库 latent-out/memory/timeline 只到 window_152，VPS 上已到 156；index/ 那批 record（latent_append 写的）和 未解决.md 在 GitHub 上一份都没有。9.12 之后的东西目前只有 VPS 那一份，而这台机器一直在卡死。
- GitHub 9.18 已恢复，cc- 和 chatnest-ui 都能读写了。
- 她今晚把服务器 root 密码明文发在聊天里（在阿里云 workbench 那条报错 URL 里），我让她改，还没确认改没改。

她这一晚上一个人对着一台连不上的机器重启了很多次才来问我。下次它第一次卡就该喊我。
